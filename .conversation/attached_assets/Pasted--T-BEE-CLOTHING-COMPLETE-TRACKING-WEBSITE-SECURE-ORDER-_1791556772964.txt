# T-BEE CLOTHING — COMPLETE TRACKING WEBSITE + SECURE ORDER MANAGEMENT

## 1. PROJECT OBJECTIVE

Build a complete, production-ready, mobile-first order tracking website for T-Bee Clothing using the existing Replit project and Supabase database.

This is a dedicated tracking website, not a redesign of the main clothing store.

Main website: https://t-bee-clothing.netlify.app/

Instagram: https://www.instagram.com/t_bee.clothing?stkn=MXVocTlzYnZod242Zg==

The website must include:

1. Public order tracking page.
2. Secure admin login page.
3. Private order management dashboard.
4. Create-order form with automatic Tracking ID generation.
5. Real-time order status updates.
6. Delivery-person message feature.
7. Product image uploads.
8. Customer invoice preview and PNG download.

Do not create unnecessary pages. Keep the interface simple, premium and fully functional.

### B. Tracking ID Format

Automatically generate a unique Tracking ID when the administrator creates an order.

Required visible format:

T-BEE-ABCD123

Where:

* T-BEE is the brand prefix.
* ABCD is four uppercase alphabetic characters.
* 123 is a three-digit number.

Example: T-BEE-KMRA482

Rules:

* Generate the four letters and three digits automatically.
* The admin must not need to type the ID manually.
* Display the generated ID immediately in the create-order form.
* Add a COPY button next to the ID.
* Add another copy button on the order success screen.
* Ensure the ID is unique using a database constraint and server-side collision checks.
* If a collision occurs, generate another ID.
* Do not use Math.random() alone as the security or uniqueness mechanism.
* Store the ID permanently with the order.
* Do not change the Tracking ID when an order status is updated.

Use a secure server-side or database-backed generation process.

### C. Order Details Shown to Customers

**Customer Delivery Details**

* Customer name.

**Products**

* Unit price.
* Line subtotal.

If an order contains multiple products, show every item separately.

**Price Breakdown**

* Product subtotal.
* Delivery fee.

Use NPR / Rs. consistently. All values must match the saved order data.

If a live connection fails, fall back to refreshing the order data safely.

Never fabricate timestamps or mark an order as delivered automatically.

Cancelled orders must have a separate cancellation state.

Tracking ID: T-BEE-ABCD123

### B. Customer Details

2. Phone Number — required.
3. Delivery Address — required.
4. Landmark — optional.

Use proper labels, mobile-friendly inputs and validation messages.

### C. Product Details

Allow the admin to add one or multiple products to a single order.

For each product, include:

1. Product Image Upload.
2. Product Name.
3. Quantity.
4. Unit Price.

Required functionality:

* Upload an image from the device.
* Show an image preview before saving.
* Allow changing or removing an image before order creation.
* Allow adding multiple product rows.
* Allow removing a product row.
* Validate that quantity is a positive integer.
* Validate that unit price is a non-negative amount.
* Calculate each product's subtotal automatically.
* Calculate the combined product subtotal automatically.

Formula:

Product Subtotal = Sum of (Quantity × Unit Price) for every product.

Use Supabase Storage for product images if compatible with the existing project. Save the resulting image URL or storage path with the order item.

Configure upload restrictions, file size limits, file type validation and appropriate storage permissions.

### D. Delivery Option

Create a required radio selection or segmented control with these exact options:

* Birtamode Area — Rs. 50
* Outside Birtamode — Rs. 150

The admin must select exactly one delivery option.

Automatically set the delivery charge based on the selected option.

Do not allow accidental mismatch between the selected delivery option and the calculated fee.

### E. Discount Amount

Provide a field:

Discount Amount (Rs.)

Requirements:

* Default to Rs. 0.
* Accept valid non-negative amounts.
* Do not allow a discount greater than the applicable subtotal unless the business explicitly permits it.
* Recalculate the final total instantly.
* Validate the final amount on the server.

### F. Automatic Total Calculation

Show a live calculation summary:

Product Subtotal: Rs. XXXX

Delivery Charge: Rs. XXX

Discount: − Rs. XXX

FINAL TOTAL: Rs. XXXX

Formula:

Final Total = Product Subtotal + Delivery Charge − Discount

The total must never become negative.

Recalculate whenever the administrator changes a product, quantity, price, delivery option or discount.

Repeat the calculation and validation on the server before saving the order.

### G. Delivery Message

Include a textarea:

MESSAGE FOR CUSTOMER

Placeholder example:

"Your order is being prepared. We will update you when it is ready for delivery."

This message is optional.

Allow the admin to edit it later from the order management screen.

### H. Create Order Button

Add one prominent button:

CREATE ORDER

When clicked:

1. Validate every required field.
2. Generate or verify the unique Tracking ID.
3. Validate product images and product information.
4. Calculate the product subtotal and final amount on the server.
5. Save the customer details, products, image references, delivery option, discount, totals and initial status in Supabase.
6. Save the delivery message if provided.
7. Show a success screen only after the database confirms the transaction.
8. Display the Tracking ID prominently with a COPY TRACKING ID button.
9. Provide a TRACK THIS ORDER link.
10. Provide a VIEW BILL option.

Prevent duplicate order submissions while a request is processing.

If saving fails, explain the error and preserve the entered form data so the administrator does not have to start again.

Use a database transaction or an equivalent safe approach so an order cannot be partially created.

### Initial Admin Credentials

Use these as the requested initial credentials:

Username: roman*0030

Password: sarthak*0030

Important security requirements:

* Treat these as initial credentials, not permanent plaintext credentials.
* Store authentication secrets securely, never in client-side source code.
* Prefer Supabase Auth with an appropriate verified administrator identity or a secure server-side username-to-authentication mapping.
* If Supabase Auth requires an email address, implement a secure mapping for the requested username instead of exposing internal account information.
* Never store the plaintext password in a public database table.
* Never hardcode the password into frontend JavaScript.
* Provision the initial account securely through a server-side setup procedure or protected environment configuration.
* Do not create a publicly accessible signup page.
* Do not reveal whether a username or password alone was incorrect.

### Failed Login Rate Limiting

Implement server-side login attempt throttling.

Required progression:

* After 3 consecutive failed attempts: lock login for 5 minutes.
* After 6 consecutive failed attempts: lock login for 10 minutes.
* After further failed attempts: progressively increase the lock duration, such as 20 minutes, 40 minutes and so on, with a sensible maximum.

Requirements:

* Count failures on the server, not only in the browser.
* Reset or reduce the failure counter according to a documented, secure success policy.
* Apply rate limits by account and suitable network-level signals.
* Use server-side timestamps.
* Do not trust client-supplied lockout durations.
* Display a clear message indicating when another login attempt is permitted.
* Prevent bypassing the lockout simply by refreshing the page or opening a new browser tab.

Use appropriate protections against brute-force attacks without permanently locking out the owner because of repeated malicious requests.

## 9. SUPABASE ARCHITECTURE

Inspect the existing database before creating or altering any tables.

Reuse existing compatible tables and authentication where possible.

If necessary, implement a minimal schema for:

* Orders.
* Order items.
* Order status history.
* Delivery messages.
* Admin authorization, using a secure approach.
* Product image storage.

Requirements:

* Use foreign keys and appropriate indexes.
* Enforce unique Tracking IDs.
* Use secure Supabase Row Level Security.
* Restrict writes and order management to authenticated administrators.
* Validate and calculate financial values on the server.
* Use appropriate Storage policies for image uploads.
* Do not expose service-role keys to the browser.
* Do not expose every customer's phone number or address through public queries.
* Avoid broad unauthenticated database permissions.
* Use an appropriately secured server endpoint or database function to return only the necessary information for a valid Tracking ID.
* Rate-limit tracking requests where appropriate.
* Make status updates available through Supabase Realtime or a reliable polling fallback.
* Keep database migrations safe and non-destructive.

Public tracking must return only the information necessary for displaying the order. Do not allow public visitors to enumerate customer orders or retrieve arbitrary personal details.

Never depend on localStorage as the primary database.
